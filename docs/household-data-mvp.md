## 2. MVPの範囲

既存Portalを入口に、購入履歴の取込と生活イベントの手入力を併用する。
初回は過去3〜6か月の購入履歴から候補を抽出し、継続補充する5〜10商品を選ぶ。
履歴を提供できない場合は手入力で同じモデルへ登録できる。

対象条件:
- 定期的に買い直す。
- 商品/容量を識別できる。
- 未開封数量と開封/使い切りを記録できる。
- 現在庫を本人が確認できる。

洗剤、シャンプー、歯磨き粉、紙類等は候補カテゴリ。ユーザーが所有しているとは仮定しない。
家具・本・服の全台帳、常時自動同期、自然言語入力、自動注文は後続とする。

## 3. 最小画面

| 画面 | 操作 | 表示 |
|---|---|---|
| 取込 | CSVを選ぶ、候補を確認、採用/除外/既存商品への紐付け | 商品候補、支出明細、欠損、重複候補、元データ |
| 商品/在庫 | 商品登録、初期在庫確認、イベント入力 | 未開封数量、使用中、実測残量、観測日 |
| 履歴 | 商品で絞り込み、訂正/取消 | 入荷・開封・使い切り等と入力元 |

履歴取込では現在庫を自動で増やさない。
初期在庫は「確認日時点の残高」として登録する。確認日時以前の取込履歴は履歴として保管し、初期残高へ再加算しない。
確認後の入荷イベントだけを残高へ反映する。

## 4. 入力シナリオと期待結果

| 操作 | 必須入力 | 期待結果 |
|---|---|---|
| 商品登録 | 名称、管理単位 | 同一商品候補を確認して作成。容量違いは区別 |
| 初期在庫 | 商品、確認日時、未開封数量、使用中の有無 | 初期残高を作成。使用中の残量は不明でも可 |
| 店頭購入 | 商品、数量、購入日（不明可） | 購入履歴を登録。同時入荷の選択時だけ在庫増加 |
| EC購入 | 商品、数量、注文日（不明可） | 購入履歴のみ。到着までは在庫を増やさない |
| 入荷 | 商品、数量、到着日時、注文との紐付け（可能な場合） | 未開封在庫を増やす。再送では増えない |
| 開封 | 商品、対象個体/ロット、発生日時（不明可） | 未開封を1つ減らし、使用中へ移す。保有総量は変わらない |
| 残量確認 | 使用中の対象、割合または量、観測日時 | 実測値を保存。過去値は履歴に残す |
| 使い切り | 使用中の対象、発生日時（不明可） | 使用中から外し、残量0として記録 |
| 訂正/取消 | 元記録、変更内容、理由（任意） | 元記録への参照を残し、在庫を再計算 |

個数は整数、内容量はg/ml/枚等の指定単位、割合は0〜1とする。
「500ml×2個」の包装内個数と注文明細の数量を混同しない。
複数の使用中商品がある場合は対象を選ぶ。推測で個体を確定しない。
購入金額・店舗・外部注文番号は任意。日付不明はnullとし、登録日時で置換しない。
発生日時不明の開封等は在庫状態には反映するが、消費期間の計算から除外する。
過去の在庫イベントを後入力した場合は初期残高との前後関係を確認してから反映する。

## 5. 取込の構成

原データ → 解析結果 → 確認済み明細 → 商品/購入/イベント

- 解析処理と在庫更新を分ける。取り込んだ行だけでは入荷を確定しない。
- 原文、入力元、元ID/行番号、取込日時、パーサーバージョンを追跡できるようにする。
- 同じデータを再取込しても件数や在庫が増えない。
- IDがない場合はファイルハッシュと行番号で完全な再取込を防ぎ、別ファイル間の重複候補は確認する。
- 日付/金額の一致だけで別ソースの行を自動統合しない。
- 公開GitHubには架空の例だけを置く。実データの保存場所と保持期間は技術選定時に定義する。

## 6. 入力元ごとの検証

MF Web CSVについて公式に示されている項目:
計算対象、日付、内容、金額（円）、保有金融機関、大項目、中項目、メモ、振替、ID。
アプリの年単位出力と同一形式とは仮定せず、どちらもサンプルのヘッダーで判定する。

| 項目 | 確認事項 | 欠損時の扱い |
|---|---|---|
| 商品名 | 内容欄が商品名か、カードの店舗名か | 店舗名だけの行は商品化しない |
| 数量・容量 | 構造化項目か、商品名内の文字か | 注文資料/本人確認で補う。数量1とは決めない |
| 商品識別子 | ASIN/JAN/型番の有無 | 既存商品の候補を提示し確認 |
| 注文番号/明細番号 | AmazonとMFの照合に使えるか | 自動照合の範囲を制限 |
| 日付 | 注文、発送、決済のどれか | 元データの日付と意味を保存 |
| 金額 | 商品代、割引、送料、返金の内訳 | 不明な内訳を推測で配賦しない |
| 振替/計算対象 | カード/通販の重複関係 | 行を残した上で支出集計の対象を区別 |
| 現在庫・開封日 | 履歴に存在するか | 本人の在庫確認/手入力 |

MFのAmazon明細は原則発送日。発送日を取得できない場合は配送予定日等が使われる。
その日付を到着日や注文日へ変換しない。
一般アカウントのAmazon出力形式、個人利用の公開API、継続自動同期は未確認。
API前提で開発しない。

検証用サンプルはCSVヘッダーと10〜30行から開始できる。
できればAmazon通販明細とカード明細が含まれる期間を使う。
本人が渡せる範囲でよく、口座情報等の不要な値は削除/置換してよい。
Amazon原本はMFサンプルで不足項目を確認してから求める。

## 7. 整合性の確認例（すべて架空）

| ケース | 操作 | 期待結果 |
|---|---|---|
| 初期残高と過去購入 | 未開封2本を確認→過去の購入10件取込 | 未開封は2本 |
| 注文と到着 | 2本注文→同じ注文の2本入荷 | 発注2本、入荷後在庫2本 |
| 開封 | 在庫2本→1本開封 | 未開封1本、使用中1本 |
| 再送 | 同じ入荷IDを2回送信 | 入荷1回分のみ |
| 取消 | 入荷2本の記録を取消 | 状態を再計算。後続開封が矛盾する場合は訂正を要求 |
| 消費記録 | 開封→使い切り | 両日時が確定する場合だけ消費日数の観測にする |
| 通販とカード | 通販商品行と同額のカード行取込 | 商品を2回購入したとは扱わない。照合不明なら候補として残す |

## 8. MVP完了条件

- 5〜10品の登録、在庫確認、イベント入力、履歴閲覧、訂正ができる。
- サンプルで取得できない項目が明示され、確認なしの推測値が混入しない。
- 再取込/再送/注文と入荷の併記で在庫が二重加算されない。
- 保存失敗をユーザーが把握できる。
- 別ユーザーのデータへアクセスできないことを確認する。
- エクスポートと復元の手順がある。
- 通常の手入力イベント10件の操作時間を計測し、中央値30秒以内を仮目標とする。
- 対象商品のうち最低1商品で開封〜使い切り〜補充の1サイクルを記録する。
- 実測と推定を区別し、履歴不足なら消費予測を未算出と表示する。
