2026-10-10。要件定義 requirements.md を維持し、ユーザーの「まず実際に試せるPoC」「要件通りに優先順位をつけて実装」に基づく。

1. Portalから既存APIの購入履歴・補充根拠・本人状態更新を操作する入口を用意する。FR-04/05/06/07/13の既存処理を画面から試す第一段階。自然言語対応の受入完了ではない。
2. #32の費用制御/Secretを統合し、#38の実AI・認証付き会話と#40の会話/補正確認を接続する。FR-06/07/08/12/13。「最後いつ買った」「そろそろ買うもの」「まだ残っている」を試せること。
3. #33〜#37のGmail注文取込・AI構造化・同一性整理と、#39の現在価格/代替提案を接続する。FR-01/02/03/09/10/11。両ECの受入後に自動取込を開始する方針を維持する。
4. #41/#42の週次取込・候補あり時だけのGmail通知、#43の継続運用検証。

最初の画面に補助的な履歴/状態表示を実装するが、会話・Gmail取込を単純なダッシュボードで代替しない。Couldの高度なダッシュボード/分析は後回し。#16を完了扱いせず、PoCに必要な実認証・本人データ分離・書込み整合は接続時に確認する。署名試験だけのToken Creator追加は保留し、既存Googleログインを使う。

## 第一段階の実装

- src/CommercePage.tsx: 履歴ページング、補充候補/全商品、平均/中央値、推定日/信頼度/理由、状態の明示保存。
- src/commerce-api.ts: Firebase ID tokenによるAPI操作。UIDを入力に含めず、トークンを保存/出力しない。401/403/通信エラー、ログイン切替を扱う。
- 状態更新は同じ画面での再試行に同じmutation ID/内容を使い、自動再送しない。画面移動/再読み込みをまたぐID保持は未提供。
- 新規依存なし。APIはVITE_COMMERCE_API_URLで指定可能。未指定時は既存Cloud Run URL。
- APIのOrigin allowlistはGitHub Pagesのみ。ローカルから実APIへの接続や本人UID追加には設定変更が必要。
- 現行Cloud Runは匿名検証UIDだけを許可しているので、本人ログインからの本番操作はまだ403となる。
- Gmail取込・実AI/検索はこの差分には含まれず、空DBに画面を追加しても価値検証完了とはしない。
- 本番公開前に本人利用のallowlist、初期データ取込、実認証でのAPI読書き、Rules/既存Portalの必要な受入を確認する。追加本番変更の具体的差分は別途提示する。
