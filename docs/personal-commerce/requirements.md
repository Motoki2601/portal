# Personal Commerce 要件定義

状態: Baseline v1.0  
最終更新: 2026-10-05

この文書をPersonal Commerce MVPの要件定義の正本とする。基本設計・実装Issueは本書を基準にする。

## 1. 背景

個人用Portalを発展させ、購買・在庫・支出に関する日常の意思決定を支援する。

現在、購入情報はAmazon、ヨドバシ、Gmail、Money Forward ME等に分散している。ユーザーは「何を最後にいつ買ったか」「そろそろ必要か」「今いくらか」を毎回自分で確認している。

将来はPersonal Commerce Agentへ発展させるが、高度なAgentic Commerce自体を目的にはしない。最小の仕組みで日常の購買判断を楽にすることを優先する。

## 2. 目的

### 主目的

過去の購買履歴と購入周期を利用し、次に必要になりそうな商品を先回りして提示する。

### 副目的

- 過去の購入履歴を横断的に参照できる
- 自分の購入頻度・傾向を把握できる
- 現在価格や代替商品を確認しやすくする
- AIへ現在使用中の商品や過去の選択を毎回説明しなくてよい状態にする

### 将来目的

- 商品探索・比較・推薦の高度化
- 購入準備
- 明示的なポリシー・上限・承認ルールのもとでの条件付き自動購入

## 3. 解決する課題

- 購入履歴が複数サービスに分散している
- 補充時期をユーザー自身が判断している
- 同じ商品を買うか代替商品へ変えるかの比較に手間がかかる
- AIがユーザーの購買履歴を前提知識として使えていない
- 家計データだけでは具体的な商品・数量・注文単位を十分に把握できない

## 4. 対象ユーザー

当面は単一ユーザーによる個人利用とする。

## 5. MVPスコープ

MVPでは次の業務フローを成立させる。

```text
Amazon / ヨドバシで購入
↓
Gmailの注文メールを取得
↓
AIが注文情報を構造化・自動確定
↓
商品を整理・同一視
↓
繰り返し購入を検出
↓
平均・中央値から購入周期を推定
↓
推定時期の約7日前から補充候補化
↓
必要時にAIが現在価格・代替商品を調査
↓
AI会話または週次Gmailで提案
↓
ユーザー自身が購入
↓
新しい購入履歴を反映
```

MVPのAgent LevelはLevel 2とする。

- Level 0: 分析のみ
- Level 1: 補充候補を提示
- Level 2: 商品探索・比較・推薦
- Level 3: 購入準備後に承認を要求
- Level 4: 条件付き自動購入

## 6. 非スコープ

MVPでは以下を行わない。

- 自動購入、カート投入、決済代行
- Payment credentialの自前保管
- 購入承認ワークフロー
- 厳密な実在庫・論理在庫管理
- ml / g単位の残量管理
- lot / individual unit管理
- 全ECサイト対応
- Money Forwardとの金融トランザクション突合を必須化
- 複数Agent協調
- MCP / A2A / UCP / ACP / AP2を前提とした実装
- 既存Portal機能の全面移行
- 本格的なDR / 高可用性構成

## 7. 入力要件

### 7.1 主要入力

- Amazon注文メール
- ヨドバシ注文メール
- ユーザーの自然言語による補正

将来的に購入履歴ファイルや他ECデータを追加してよい。

### 7.2 Gmail取込

- 注文メールは少なくとも週1回程度まとめて取得できればよい
- リアルタイム取込は要求しない
- AIが注文情報を構造化する
- 抽出結果は原則としてユーザー確認なしで自動確定する
- 必須項目、型、重複等の機械的チェックは行う
- 不明な値は推測で埋めず、null / unknown等として扱う
- 元メールとの対応関係を保持し、後から訂正できること

### 7.3 Amazonの購入日ルール（2026-10-05）

Amazonの物品注文確認（「注文済み」メール）では、本文に明示された注文日があればそれを優先し、なければGmail internalDateをAsia/Tokyoへ変換した受信日をorderedOn（購入日）として採用する。これはユーザーが指定したMVP業務ルールであり、メール本文の日付と取得根拠を区別する。発送・配達・広告・転送メールやデジタル注文へ一律適用しない。受信遅延等により実際の注文日とずれる場合はユーザーが訂正できる。

### 7.4 ユーザー補正

自然言語で以下のような補正ができること。

- 「まだ残ってる」
- 「昨日使い切った」
- 「予備がある」
- 「もうこの商品は使っていない」
- 「今はこの商品を使っている」

## 8. 出力要件

### 8.1 AI会話

以下を自然言語で問い合わせられること。

- 「そろそろ買うものある？」
- 「このシャンプー最後いつ買った？」
- 「いつもどの洗剤を買ってる？」
- 「今いくら？」
- 「別のシャンプーに変えたい」

AIは必要な購入履歴を自動参照して回答する。

### 8.2 Push / 定期レポート

- 週1回程度、補充候補を判定する
- 補充候補がある場合はGmailへレポートを送る
- 原則として候補がない場合は送信しない
- レポートには推定根拠、現在価格、必要に応じた代替候補を含める

## 9. ユースケース

- UC-01: 補充時期を検知する
- UC-02: 同一商品の現在価格を確認する
- UC-03: 代替商品を提案する
- UC-04: 過去の購入履歴を問い合わせる
- UC-05: 現在価格を問い合わせる
- UC-06: 現在利用中の商品を前提に商品変更を相談する
- UC-07: ユーザーが現在状態を自然言語で補正する

## 10. 機能要件

### Must

- FR-01 購入履歴取込
- FR-02 AIによる注文情報の構造化・自動確定
- FR-03 商品同一性・カテゴリ整理
- FR-04 購入周期分析
- FR-05 補充候補検知
- FR-06 状態のユーザー補正
- FR-07 購入履歴問い合わせ
- FR-08 ユーザーコンテキスト解決
- FR-09 AIによる必要時の現在価格取得
- FR-10 同一商品の再購入提案
- FR-11 代替商品提案
- FR-12 AI会話インターフェース
- FR-13 提案理由の提示

### Should

- FR-14 週次Gmailサマリー
- FR-15 条件付き通知
- FR-16 新規購入後の履歴反映
- FR-17 推定信頼度の表示
- FR-18 商品変更履歴

### Could

- Money Forwardとの金融トランザクション突合
- 月次・カテゴリ別支出分析
- 価格推移可視化
- セール検知
- ポイント込み実質価格比較
- レビューを含めた推薦
- Portal上のダッシュボード
- Gmail以外の通知チャネル

## 11. データ要件

### 11.1 最小データ概念

MVPでは以下を基本とする。

- PurchaseOrder: 注文単位
- PurchaseLine: 注文明細単位
- Product: 購入・比較に使う商品単位
- ProductState: 粗い現在状態
- UserObservation / Correction: ユーザー補正と訂正履歴
- ReplenishmentEstimate: 補充時期の推定
- Recommendation: AIによる提案
- Source / Import Metadata: 元メール・取込元・重複防止情報

### 11.2 商品

MVPではProductとProductVariantを分離しない。

商品には必要に応じて以下を持つ。

- canonical name
- 元データ上の商品名・表記揺れ
- category
- brand
- 容量・単位
- replenishment status

補充対象状態は以下を想定する。

- unknown
- candidate
- active
- excluded

AI判定とユーザー判断を区別し、ユーザーが明示した判断をAIが勝手に上書きしない。

### 11.3 商品同一性

AIは以下を材料に同一商品候補を判定する。

- ブランド
- 商品名
- カテゴリ
- 容量
- 本体 / 詰替等の包装差
- 型番、JAN等が取得できる場合はその識別子

容量や包装が異なる場合は原則として別Productとして扱う。誤統合はユーザーが訂正でき、ユーザー訂正をAI判定より優先する。

### 11.4 現在使用中商品の判定

優先順位は以下とする。

1. ユーザーが明示した現在使用商品
2. 同カテゴリの直近購入商品
3. 同カテゴリの購入履歴からの推定
4. 不明

同カテゴリの商品を短期間に複数購入して一意に判定できない場合は、勝手に確定しない。

### 11.5 在庫・利用状態

MVPでは厳密な個数・残量を維持しない。必要に応じて以下の粗い状態を扱う。

- unknown
- likely_available
- running_low
- spare_available
- out_of_stock

ユーザー補正をAI推定より優先する。

### 11.6 事実と推定の分離

以下を区別する。

- 購入日・購入商品: 事実
- 平均・中央値による購入周期: 算出値
- 次回補充時期: 推定
- 商品推薦: AI判断

推定を購入事実として保存しない。

## 12. 業務ルール・推定要件

### 12.1 補充対象候補

以下を組み合わせてAIが候補を抽出する。

- 同一商品の複数回購入
- 同カテゴリ商品の継続購入
- AIによる消耗品判定
- ユーザーによる明示指定

AIが候補を出し、必要に応じてユーザーがactive / excludedを確定する。

### 12.2 購入周期

- 連続する購入日の差分から購入間隔を算出する
- 平均値・中央値を基本的な代表値とする
- 同一商品の履歴を優先する
- 同一商品データが不足する場合は同カテゴリ履歴を参考にしてよい
- 高度な需要予測モデルは要求しない

### 12.3 データ不足・外れ値

- データ不足時は無理に高精度な推定を行わない
- 外れ値があることを許容する
- 平均値と中央値の乖離等を不確実性として扱ってよい

### 12.4 「そろそろ」の判定

推定次回購入時期のおおむね7日前から補充候補とする。

厳密な在庫切れ日を保証するものではなく、購買判断を促す参考情報として提示する。

### 12.5 現在価格・代替商品

- 常時価格収集は行わない
- 補充候補になった時、またはユーザーが問い合わせた時にAIが調査する
- 商品価格、容量、単価、送料等の取得可能な情報を比較する
- 取得できない項目は推測しない

## 13. 外部連携要件

### MVP

- Gmail: Amazon / ヨドバシ注文メールの取得、週次レポート送信
- AIサービス: メール構造化、自然言語会話、商品・価格調査、推薦
- ECサイト: ユーザー自身が購入を実行する

### 将来

- merchant API
- checkout handoff
- MCP / UCP / ACP / A2A / AP2等
- 条件付き購入実行

特定protocolをMVPの前提にしない。

## 14. 非機能要件

### Security / Privacy

- 実個人データを公開GitHubへ保存しない
- GitHubにはコード、仕様、匿名fixtureのみ置く
- AIへDB全体の無制限な権限を与えない
- AIは許可されたApplication操作を経由して読み書きする
- secretをコードや公開リポジトリへ保存しない

### Data Integrity / Audit

- AI抽出結果は原則自動確定してよい
- 保存前に型、必須項目、重複等を検証する
- 同一注文の二重登録を防止する
- 重要な更新は、いつ・何を・どの入力を根拠に変更したか追跡可能とする
- 誤更新を元データや更新履歴から訂正・復元できること

### Cost

- 通常利用時の月額は1,000円程度以内を目標とする
- Budget Alert等で異常課金を検知できること

### Performance

- 厳密なSLAは設けない
- DB参照は数秒程度、AI分析・商品検索は一般的な生成AIサービスとして許容できる速度でよい

### Availability / Recovery

- 24/7高可用性は要求しない
- 本格的なDRはMVP対象外
- 元メール等から再取込できることを重視する

## 15. 運用要件

- ユーザー自身がSQLを書かずに運用できること
- 日常の入力は自動取込またはAIとの自然言語会話を基本とする
- AIの誤りは自然言語または管理機能から訂正できること
- 大規模な運用監視体制は不要

## 16. 将来拡張

- 商品探索・推薦精度の高度化
- Point / Coupon / 送料込みの総コスト最適化
- Money Forward等との支出突合
- 厳密な在庫イベント管理
- ProductVariant分離
- 購入準備・checkout handoff
- ユーザー承認を伴う購入実行
- 条件付き自動購入
- 外部Agent / Commerce protocol連携

将来拡張のためだけにMVPを複雑化しない。YAGNIを優先する。

## 17. 未決事項

要件レベルの主要事項はBaseline v1.0として確定した。

以下は基本設計で決定する。

- Gmail取得・定期実行の具体方式
- Firestoreのcollection / document構造
- Application API / Tool境界
- AI provider / modelの使い分け
- 現在価格調査の具体的な実装方式
- 週次処理・メール送信の実行方式
- Cloud StorageをMVPで利用するか
- BigQueryをMVPで利用するか

## 18. 受入条件

MVPは少なくとも以下が一連で成立した時点で価値検証可能とする。

1. Amazonまたはヨドバシの注文メールから購入履歴を取り込める
2. AI抽出結果を重複なく自動確定できる
3. 同一・類似商品の購入履歴を整理できる
4. 平均・中央値による購入周期から補充候補を提示できる
5. 「最後にいつ買ったか」を自然言語で問い合わせられる
6. 必要時に現在価格を調査できる
7. 同一商品または代替商品を理由付きで提案できる
8. ユーザーが状態を自然言語で補正できる
9. 週次で補充候補を判定し、候補があればGmailへ通知できる
10. AI書込の重複を防ぎ、更新履歴を追跡・訂正できる
